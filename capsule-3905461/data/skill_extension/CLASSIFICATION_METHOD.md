# Category classification method

For every matched pair, inspect application-specific workflow logic, data representation/persistence, UI/form definition, validation, integration and startup configuration against the same existing taxonomy. Link retained source fragments to the available implementation/model-generation histories. Record concrete facets, rather than treating a language name as a substitute for everything programmed in that language. An AI-created function, predicate or data structure is classified under the same rules as a human-created one.

Keep two positive evidence classes: **O**, observed use or an attributed action report; **R**, a technical requirement supported by the chosen implementation. The main involved-skill profile is the distinct-label union O ∪ R within common-task/starter-adaptation scope. Display O, R or O/R with user allocation and source references. Do not call R an observed work event. Attribution to AI from an implementation report is contextual, not line-level authorship; use uncertain where attribution cannot be made. Unknown cells are not negatives. Observed-only columns describe the O subset; the primary profile uses the O/R union. Repeated events, repeated labels in multiple lifecycle contexts, and multiple users never increase the distinct-label union.

The source taxonomy includes both broad and narrow concepts: a language, functions and expressions are separate labels but overlap in abstraction. The resulting inventory is a description of technical content, not an additive difficulty, independent-dimensions, expertise or effort scale. Do not count it as 209 independent technologies. No platform-level indicator or expert weight is imported.

## Operational mapping decisions

| Facet | Existing taxonomy mapping | Evidence rule |
|---|---|---|
| Language | TypeScript, JavaScript; Python GAP04 | Located application/helper source plus work-history context. Do not hide Python because the taxonomy omits it. |
| Boolean/comparison logic | SK131 Expressions | A located programmed predicate; a business phrase such as “approved” alone is insufficient. |
| Branching control | SK046 Control Structures | Explicit code if/switch/conditional control **or** a formal model gateway with outgoing flows. The broad category is applied to both representations. |
| Workflow state representation | SK058 Custom Process Model; SK056 +BPMN Process Model | Custom application state/transition structures versus formal BPMN. The runtime's own transition-engine implementation is excluded. |
| Functions | SK138 Functions | Application function/method or callback definition, not merely use of a library whose internals have functions. |
| Iteration | SK141 Iteration Statements | Explicit loop or application-authored collection traversal callback/comprehension; the extended operational reading is disclosed. |
| Types | SK133/SK104 IT Data Types | Technical string/number/boolean/union/array declarations, conversions or form component typing. |
| Data structure | SK011 Data Structure | Located application record/schema structure, including Model nested form-data schemas; not an assertion of physical database-schema work in Model. |
| Entity type | SK136 Entity Types | Explicit application entity/interface/class, not every generic JSON object. |
| Constraints | SK010 Constraints | Explicit persistent identity/null/default/integrity constraints in schema/DDL. |
| Enumerations | SK137 Enumerations | Programmed enum or finite literal type domain. Merely mentioning business alternatives is insufficient. |
| Form choices | SK032 +Lookup/Drop-down | Actual technical choice-control configuration in either strategy; human requests retain their original business/IT ambiguity. |
| Fields | SK115 Data Fields | Named application input binding or schema field/validation configuration, regardless of actor or strategy. |
| Variables | SK110 or SK055 Variables | Explicit application UI/logic variables; variable names embedded in reusable runtime internals do not qualify. |
| Formulas | SK049 Formulas | Located arithmetic calculation such as date duration or identifier sequence. An arbitrary expression is not additionally classified as a formula. |
| Queries/integration | SK151 Query Functions, SK083 Data Source Integration | Authored query predicates/calls and application-to-storage binding. ORM use is not automatically SQL authoring. |
| Markup/style | SK103 HTML, SK100 CSS/SCSS | Located application markup (including JSX HTML tags) or authored CSS/style properties. Reused UI component implementation is excluded. |
| JSON/XML | SK145 JSON, SK156 XML | Explicit structured schema/serialization or documented source interpretation. JavaScript/Python objects alone do not establish JSON. Exported BPMN XML alone does not identify who handled XML. |
| Configuration/startup | SK132 CLI, SK191 URL Configuration, SK199 Docker | Located application commands, endpoint address configuration or container integration; not authorship of the underlying infrastructure. |

Design-stage IDs describe a technical design facet embodied in the implementation, not an inferred separate historical design phase. IDs/names and source lifecycle contexts are preserved. These operational interpretations are documented because the workbook supplies labels and field definitions, not detailed behavioral definitions for every skill.

## Scope and interpretation

Prior Aurea, database, framework and library development remain excluded symmetrically. Application integration with them remains included. Standalone Role Call remains excluded, and additional diagram-preview evidence remains separate. No new application execution or correctness result is claimed. A tested/accepted application is not proof of any user's independent competence. AI is treated as an application-creating user for activity classification, not as possessing human learning difficulty or professional qualifications.

JSON and XML used solely as process/form serialization formats are excluded from the skill inventory. Graphical model and form tools provide these representations; generating the serialized files with AI does not make the formats user skill requirements. Technical control, field, data-structure and type definitions remain included. Code T02 has separate evidence of line-addressed XML source interpretation. Python remains a transparent taxonomy extension.


The IT subtotal applies the explicit mapping in ../skill_classification/p2_category_mapping.csv before exact-name deduplication. All 329 annotation rows and their original evidence fields are retained.

Role/executor configuration and business/UI requests for date pickers or text fields are non-IT activities. Interface-based functional scenario checks do not establish source editing or database inspection. Code insertion, environment setup and server launch may be activity-supported when their execution is evidenced, without inferring independent authorship of supplied code or commands. Unsupported SQL candidates and out-of-scope Role Call records are excluded. Excluded records remain retained and do not enter positive category sets.
